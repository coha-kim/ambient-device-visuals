# Choose Low-Resolution Fields for Pi Metaballs

The lowest-cost architecture for this 1024×600 ambient display is **CPU physics plus a low-resolution scalar field rendered to a reusable Canvas 2D pixel buffer, then upscaled once**. A 256×150-ish field gives organic merged blobs without a blur filter, uses no steady-state WebGL/GPU work, and reduces naïve field sampling to roughly **38,000 cells × 15 blobs ≈ 570,000 influence evaluations per update**; update it at 15–30 Hz and present the already-rendered image at display cadence. This is an engineering recommendation, not a Pi 5 benchmark. A one-pass WebGL fragment shader is the best second architecture when CPU time or Canvas pixel writes are the bottleneck, but it still consumes GPU and therefore cannot be asserted to use less GPU than the existing SVG blur/threshold path without measuring the deployed browser. CPU marching squares is appropriate only when an explicit contour path is required; fluid/advection is a richer motion technique, not a cheaper metaball renderer. The three user references were not available in the repository or received context, so this report does not attribute claims to them and instead uses representative, accessible sources plus the checked-in sketch.

## The shared scalar field, not blur, creates the merged organic boundary

An organic metaball is an implicit contour: each blob contributes a radial influence and the renderer sums those influences, showing the region above an isovalue. Jamie Wong’s canonical 2D formulation is \(f(x,y)=\sum_i r_i^2/((x-x_i)^2+(y-y_i)^2)\), with the visible boundary at \(f=1\) ([Jamie Wong, “Metaballs and Marching Squares”](https://jamie-wong.com/2014/08/19/metaballs-and-marching-squares/#the-math)). When two contributions raise the field above the threshold in the gap, the contour forms a neck; no separate “merge geometry” is needed. The same visual principle underlies the current implementation, although it uses one shared raster of radial-gradient discs followed by `feGaussianBlur` and a steep `feColorMatrix` alpha threshold ([current `sketch.js`](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js)).

**Measured/source fact:** the checked-in project has three populations of five blobs, a 1024×600 canvas, and two 512×300 merge buffers (`MERGE_BUFFER_SCALE = 0.5`) before one upscale ([project README](https://github.com/seoha-kim/ambient-device-visuals/blob/main/README.md); [current `sketch.js`](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js)). **Engineering inference:** a replacement should preserve that single shared-field concept rather than draw 15 independent SVG elements or attempt to make circles “stick” through physics. Rendering determines the instantaneous contour; the current separation solver still determines whether centers remain close enough for a bridge. If persistent bonding is required, it needs simulation state (for example, a short-lived bond/cluster rule), not a more expensive renderer.

The three supplied references cannot be compared source-by-source: their URLs, files, and identities are absent from the received task and repository. Repository search found local notes and public links, but no recoverable set of three external references. The representative substitutes used here are Wong’s scalar-field/marching-squares article, LeandroSQ’s CPU/WebGL per-pixel metaballs, the `gmjoseph/marching-squares-p` 2D implementation, and public GPU fluid implementations. Their demonstrations and benchmarks are evidence about algorithm structure, not Raspberry Pi 5 measurements.

## Four architectures shift cost between pixels, cells, and passes

| Architecture | Dominant work per update | Organic merge quality | GPU/WebGL use | Decision |
|---|---:|---|---|---|
| CPU scalar field + marching squares | \(O(W_gH_gN)+O(S)\) | Explicit contour; resolution-dependent | None required | Use only for a path/mesh |
| Canvas 2D raster field | \(O(WHN)\) naïvely, or \(O(WHk)\) with culling | Direct filled field; soft threshold/upscale | Browser-dependent implementation; no WebGL required | Lowest-GPU baseline at reduced resolution |
| WebGL fragment-shader field | \(O(WHN)\) fragments | Direct filled field; no CPU contour list | One fullscreen pass; GPU arithmetic/fill | Best CPU-saving fallback |
| Fluid/advection | \(O(GP)\) plus injection, where \(P\) is several full-grid passes | Trails, history, vortices | Usually many GPU passes/textures | Use only for fluid motion |

Here \(N\) is active blobs, \(W_gH_g\) is the sampled field, \(W H\) is the raster target, \(S\) is emitted contour segments, \(k\) is the average number of candidate blobs after spatial culling, and \(G\) is a fluid grid. The asymptotic terms are engineering derivations from the cited algorithms, not benchmark results.

CPU scalar field plus marching squares samples the field at grid corners, classifies each 2×2 cell into one of 16 cases, interpolates crossed edges, and emits line segments or filled polygons ([Wikipedia, Marching squares](https://en.wikipedia.org/wiki/Marching_squares); [Wong bundle](https://jamie-wong.com/javascripts/metaball.bundle.js)). At 256×150 cells there are **37,995 cells** and approximately 38,000–38,300 corner samples, so 15 blobs require about **0.57 million** naïve contributions per update. At 320×188 cells there are **60,160 cells**, or about **0.90 million** contributions for 15 blobs. A 512×300-sized field has roughly **153,000 cells** and about **2.3 million** contributions. The contour scan is only \(O(G)\), but interpolation, segment-buffer writes, and Canvas path/polygon rasterization add work that a filled field does not need. Marching squares is therefore the right choice for collision, hit-testing, SVG export, or a semantic contour—not merely to put pixels on an ambient screen.

Canvas 2D raster field evaluates the same summed influence into an `ImageData` buffer and calls `putImageData`; MDN specifies that `ImageData.data` is a four-channel `Uint8ClampedArray` ([MDN ImageData](https://developer.mozilla.org/en-US/docs/Web/API/ImageData); [MDN putImageData](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/putImageData)). At the existing 512×300 internal size, 153,600 pixels × 15 blobs is about **2.30 million** influence evaluations per update. At 256×150 it is **38,400 × 15 ≈ 576,000**, about one quarter of the pixel work. At native 1024×600 it is **9.22 million** per update and should not be the default CPU target. The low-resolution Canvas route can use a threshold plus `smoothstep`-like color mapping and nearest or bilinear upscale; it gives a true shared field without SVG filter-region expansion or DOM/filter bookkeeping.

WebGL evaluates the field once per covered fragment in a fullscreen draw. A small array or texture carries centers, radii, and colors; the fragment shader sums the active blobs and maps the result to the edge/color ([MDN GLSL shaders](https://developer.mozilla.org/en-US/docs/Games/Techniques/3D_on_the_web/GLSL_Shaders); [LeandroSQ GPU renderer](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/gpu-renderer.js)). At 1024×600 and 60 displayed frames per second, a fullscreen path covers approximately **36.9 million fragment locations per second before shader instruction cost**; this is arithmetic, not measured Pi throughput. Rendering internally at 256×150 reduces that coverage by 16×. A shader avoids JavaScript per-pixel loops, contour segment allocation, and CPU readback, but it still spends GPU cycles. MDN warns that `readPixels()` can cause a finish-and-round-trip stall, so the steady-state path must remain GPU-to-display ([MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)).

Fluid/advection is not a lower-cost way to make blobs merge. Stable-fluids-style solvers use advection, forces, divergence, pressure iterations, projection, and dye advection; representative WebGL implementations maintain multiple ping-pong framebuffers and configurable pressure passes ([Stam, Stable Fluids](https://www.dgp.toronto.edu/public_user/stam/reality/Research/pub.html); [PavelDoGreat fluid source](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/master/script.js)). **Engineering inference:** even a 128–256-wide fluid grid touches the whole grid several times per step, and dirty rectangles lose value because advection transports information. Use it only when smoke-like history, vortices, or trails are a requirement. For ordinary merged blobs, a direct scalar field is both simpler and cheaper.

## Reduced grids beat full-resolution blur for predictable cost

The recommended baseline is CPU-side physics, a reusable 256×150 field buffer, and one Canvas 2D upscale to 1024×600. Evaluate a compact-support kernel where possible so a cell outside a blob’s influence contributes zero, and maintain a uniform spatial bin or per-blob bounding box to reduce the average candidate count from \(N\) to \(k\). The exact inverse-square field is unbounded, so a practical implementation can use a cutoff chosen to match the current blur’s visual reach; changing the cutoff changes the look and must be screenshot-compared against the SVG reference. **Engineering inference:** 256×150 is a sensible starting point because it is one quarter of the existing 512×300 pixel area while retaining enough samples for broad ambient blobs; test 160×94, 256×150, 320×188, and 512×300 rather than treating any grid as universally correct.

For Canvas, allocate `ImageData` and its typed array once, write packed RGBA values in place, and issue one `putImageData` per update. Store blob centers, radii, and colors in `Float32Array`/integer arrays; use a 16-entry marching-squares table only if extracting contours; avoid per-cell objects, temporary arrays, closures, strings, SVG path construction, and repeated canvas/context creation. For a raster-only path, do not run marching squares at all. If the field is rendered at 15–30 Hz, use `requestAnimationFrame` only to present/upscale and advance motion from its timestamp, not from an assumed frame count ([MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)).

Dirty regions can reduce CPU work when movement is local: union each blob’s old and new influence rectangle, expand it by the cutoff radius, and recompute intersecting cells. **Engineering inference:** with 15 continuously wandering blobs whose influence regions cover most of the display, dirty-region savings approach zero; they are valuable during sparse motion or idle periods, not a universal optimization. Frame decimation is more dependable for an ambient display: simulate and recompute the field at 15–30 Hz, reuse the last field between updates, and keep visual output at the panel cadence if needed. This sacrifices temporal smoothness before it sacrifices topology and is preferable to running an expensive blur or solver every repaint.

If CPU measurements exceed the kiosk budget, port the same field equation to one WebGL fullscreen pass. Keep the active-ball loop bounded and fixed for driver-friendly shader compilation, upload positions/radii once per frame, use a single fullscreen triangle/quad, and avoid CPU readback. Render at a reduced internal resolution first, then upscale. `OffscreenCanvas` can move Canvas or WebGL work to a worker, but it changes responsiveness rather than the total arithmetic and adds browser/worker compatibility variables ([MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)). It should be introduced only after profiling shows main-thread contention.

## Pi 5 capability supports WebGL but proves no browser speed

**Measured/source fact:** Raspberry Pi’s product documentation lists a quad-core 2.4 GHz Cortex-A76 CPU, VideoCore VII graphics, OpenGL ES 3.1, Vulkan support, and dual 4Kp60 display capability ([Raspberry Pi 5 product page](https://www.raspberrypi.com/products/raspberry-pi-5/); [Pi 5 product brief](https://pip.raspberrypi.com/documents/RP-008348-DS-3-raspberry-pi-5-product-brief.pdf)). Those are platform capabilities, not measurements of Chromium’s Canvas 2D implementation, SVG filter path, WebGL shader throughput, or sustained watts. Browser acceleration depends on the OS image, Chromium build, Mesa/V3D path, compositor, canvas backing size, and context features. Test `webgl2` and `webgl` at startup, inspect the active renderer in the deployed browser, and retain a fallback; do not infer WebGL 2 or hardware acceleration from the board specification alone.

The 1024×600 target is far below the advertised display output, but that does not establish a frame-rate guarantee. Pi 5 guidance recommends an adequate USB-C supply and active cooling for best performance ([Raspberry Pi 5 product page](https://www.raspberrypi.com/products/raspberry-pi-5/)); **engineering inference:** a continuously animated kiosk should be tested cold and after at least 10 minutes at steady state, because thermal and power conditions can change sustained clocks. Compare the current SVG backend, low-resolution Canvas field, and WebGL field at equal visual quality and update rate. Record median and p95 frame time, dropped frames, CPU/GPU utilization, temperature, power if available, context type/renderer string, and whether the browser reports acceleration. No source found here supplies an apples-to-apples Pi 5 result.

The current SVG baseline is already optimized relative to naïve DOM metaballs: one shared 512×300 buffer, one blur/threshold pass, and one upscale. **Measured/source fact:** the repository does not contain a Pi 5 benchmark validating its claim that SVG filters are GPU accelerated; its context explicitly leaves hardware performance unverified ([project context](https://github.com/seoha-kim/ambient-device-visuals/blob/main/CONTEXT.md)). **Engineering inference:** the CPU low-resolution field is the most defensible “less WebGL/GPU” architecture because it intentionally avoids WebGL and avoids a Gaussian filter, but it could consume more CPU than the SVG compositor. A WebGL field is likely the best CPU-saving option, not a proven lower-GPU option. Only target-device measurement can establish which consumes less total energy.

## Conclusion

Start with **CPU physics + 256×150 typed-array scalar field + one Canvas 2D upscale**, preserving the existing 15-blob motion and using a cutoff/spatial bins, reused buffers, and 15–30 Hz field updates. This is the lowest-cost architecture in the specific sense requested—organic merging with no steady-state WebGL/GPU dependency—while keeping the field equation explicit and its cost predictable. Add marching squares only for actual contour semantics, not raster output; add fluid/advection only for fluid history and trails.

If profiling shows the CPU path misses frame pacing, use the same field as a single reduced-resolution WebGL fragment pass and keep all output on-GPU. Treat “WebGL is faster” and “WebGL uses less GPU than SVG” as hypotheses until the exact Pi 5, browser, driver, cooling, and kiosk compositor are measured. The missing three references remain an explicit evidence gap; the representative sources above establish algorithm behavior and API/platform constraints, while the deployment benchmark must decide the final backend.
