# Organic metaballs Raspberry Pi fluid simulation repository

## Actual algorithm and data structures

### Takeaway
This is a genuine sampled 2D metaball field plus marching-squares contour fill, but the motion is a rigid-body particle toy rather than a fluid solver. The organic silhouette is generated by summing inverse-square influence kernels on a grid and filling thresholded cells; the persistent motion comes from Matter.js rigid bodies, walls, restitution, gravity, and an optional mouse-controlled attractor.

### Cited Findings
- The README explicitly describes the project as “A toy 2D fluid simulation with physically simulated rigidbody metaballs and marching squares contour detection”; its stated goal is implementing marching squares and learning metaballs. [README](https://github.com/mx0c/metaball-fluid-simulation/blob/master/README.md)
- The page loads p5, Matter.js, matter-attractors, jQuery, and Bootstrap as local browser scripts. [index.html](https://github.com/mx0c/metaball-fluid-simulation/blob/master/index.html)
- `script.js` fixes the simulation/drawing area at `w = 650`, `h = 700`, defaults to `res = 7`, `threshold = 3`, and creates `cols = parseInt(w / res + 1)` and `rows = parseInt(h / res + 1)`. At defaults this is 93×101 grid samples and 92×100 cells. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- The scalar field is stored in a JavaScript 2D array `data[i][j]`. Each grid sample calls `getMetaballDistance(x,y)`, which sums `ball.r ** 2 / ((ball.x-x) ** 2 + (ball.y-y) ** 2)` over every ball. This is a true field evaluation on sampled points, specifically a sum of inverse-square radial kernels; it is not a bitmap blur or a precomputed texture. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Each `Ball` owns a Matter circle body, keeps a scalar radius (`this.r = 2*r`) for the field/display, and copies the body's position into `this.x`/`this.y` in `update()`. The original constructor radius is passed to `Bodies.circle`; the visual debug circle uses diameter `this.r`, so the field/display influence radius is twice the physics body's radius. [ball.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/ball.js)
- `initParticles()` creates `particleAmt` balls (default 75) at random x positions and y positions in `[80,100]`, with radii in `[minParticleSize,maxParticleSize]` (defaults 7–15). Reinitialization removes prior bodies from the Matter world. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- The world has four static boundary boxes plus a static diagonal rectangular obstacle (`w/2,h/2-50,w/2,100,PI/4`). `Box` wraps `Bodies.rectangle(...,{isStatic:true,angle})`; its `show()` draws the body in p5. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [box.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/box.js)
- Matter.js is a “JavaScript 2D rigid body physics engine for the web,” and the code advances it once per animation frame with `Engine.update(engine)`. [Matter.js README](https://github.com/liabru/matter-js/blob/master/README.md) · [Engine docs](https://brm.io/matter-js/docs/classes/Engine.html#method_update)
- The optional attractor is itself a Matter circle at the canvas center. When the mouse is pressed, gravity scale is set to zero and `attractorGravity = 1e-6`; the attractor plugin returns `(bodyA.position - bodyB.position) * attractorGravity` as a force for each body. Dragging translates the attractor toward the mouse; release restores gravity scale `0.001` and disables attraction. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [matter-attractors README](https://github.com/liabru/matter-attractors/blob/master/README.md)

### Inferences
- Default field work is approximately 9,393 samples × 75 balls = 704,475 kernel evaluations per frame, before contour interpolation and drawing. At the UI minimum `res=1`, it becomes 456,351 samples × 75 ≈ 34.2 million evaluations/frame; at `res=20`, it is only 1,188 × 75 = 89,100. These counts follow directly from the source's grid formulas and particle default. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- `data` is a sparse/dynamic JavaScript array rather than a typed array or GPU buffer. There is no spatial hash, quadtree, field texture, shader, or mesh buffer in the repository. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)

### Gaps
- The repository supplies no benchmark, frame-time profile, Raspberry Pi measurement, or browser compatibility matrix; any Pi performance estimate must therefore be treated as an algorithm-derived recommendation, not a measured result.

## Contour generation and rendering path

### Takeaway
The renderer uses CPU-side marching squares over the sampled scalar field and immediately fills p5 2D polygons/triangles per cell. It does not produce a reusable contour mesh, use a fragment shader, or invoke WebGL; p5's default `createCanvas(w,h)` mode is the 2D renderer unless `WEBGL` is explicitly passed, and this code does not pass it.

### Cited Findings
- `setup()` calls `createCanvas(w,h)` with no renderer argument and attaches the resulting canvas to `#canvas`; p5 documents that `WEBGL` must be passed explicitly to select WebGL, while the default is the normal 2D canvas renderer. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [p5 createCanvas](https://p5js.org/reference/p5/createCanvas/)
- For every cell, the code reads corner samples `a,b,c,d`, converts each to a 4-bit state using `value > threshold`, and skips state 0. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Edge crossings are estimated by linear interpolation: `(threshold-a_value)/(b_value-a_value)` and analogous expressions for the other three edges. If the UI `lerp` checkbox is disabled, crossings are replaced by the cell midpoint (`x+halfRes` or `y+halfRes`). [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- `drawSquareState()` contains cases 1–15. It draws filled triangles for simple cases, and p5 `beginShape()`/`vertex()`/`endShape()` polygons for composite cases; state 15 fills the whole cell with `rect(x,y,res,res)`. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- p5 documents `beginShape()`/`endShape()` as building a custom shape from vertices and says the default `PATH` traces its edges; this matches the repository's immediate polygon filling approach. [p5 beginShape](https://p5js.org/reference/p5/beginShape/)
- The Matter engine is not rendered through Matter.Render. The repository draws all contour polygons, optional circles, obstacles, and FPS text directly with p5 (`background`, `triangle`, `beginShape`, `rect`, `circle`, `text`). Matter.Render is an optional canvas renderer intended mainly for development/debugging, but the repo does not load or call it. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [Matter Render docs](https://brm.io/matter-js/docs/classes/Render.html)
- The only browser UI controls are threshold, grid resolution, particle amount, particle visibility, interpolation, and min/max particle size. [index.html](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/index.html)

### Inferences
- This is a contour/mesh *approximation* in the rendering sense: the continuous inverse-square field is sampled at grid corners, and each cell is replaced by one of 15 hard-coded filled polygons. It is not a polygonal mesh passed to a GPU; geometry is regenerated and rasterized through p5's immediate-mode 2D canvas each frame. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Ambiguous marching-squares states 5 and 10 are each emitted as one polygon path, with no explicit asymptotic-decider or center-value test. Thus topology at saddle cells is a visual approximation and can connect regions differently than a fully disambiguated contour implementation. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- With `lerp` off, the contour is visibly more blocky because every crossing is placed at a cell midpoint; with it on, edge crossings move according to the scalar values. This is geometric interpolation only, not temporal smoothing or fluid advection. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)

### Gaps
- The source does not state whether the deployed GitHub Pages browser serves a hardware-accelerated 2D canvas on Raspberry Pi, and it does not provide GPU/shader code or a WebGL fallback.

## Fluid semantics, persistence, and Raspberry Pi 5 recommendations

### Takeaway
Despite the “fluid simulation” label, there is no fluid state or advection step: particles are independent rigid bodies. Persistent organic forms arise from persistent body positions/velocities and overlapping metaball fields, while separated circles occur when particles' summed field drops below the threshold. For a Pi 5 browser, preserve a moderate grid and particle count first; do not treat lower `res` as a quality setting without accounting for its inverse cost.

### Cited Findings
- The only per-frame simulation update is `Engine.update(engine)`, followed by field sampling and contour drawing. There is no velocity field, semi-Lagrangian advection, pressure projection, viscosity, diffusion, density transport, boundary-condition solver, or fluid grid in `script.js`. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Matter bodies use `friction: 0` and `restitution: 0.85`; the engine's default gravity is later scaled to `0.001` on mouse release. These choices create bouncing/sliding rigid particles, not fluid-like momentum transfer or incompressibility. [ball.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/ball.js) · [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- The attractor force is enabled only during mouse press/drag and is disabled on release; therefore persistent clustering is not continuously driven by the attractor. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [matter-attractors README](https://github.com/liabru/matter-attractors/blob/master/README.md)
- The scalar field is additive: each ball contributes `r²/d²`. Nearby balls therefore raise the field above the threshold in the region between them; farther-apart balls can fall below it and render as separate components. This is the source-level reason the image can look like a single organic blob or separated circles. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Debug particle circles are conditional on `showParticles`; the contour is always drawn. Therefore a separated round-looking component normally comes from the threshold contour of one ball, not necessarily from the optional debug-circle path. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- The repository's package manifest pins an old-era stack: Matter.js `^0.12.0`, matter-attractors `^0.1.6`, and p5 `^1.1.9`. [package.json](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/package.json)

### Inferences
- “Persistent organic shapes” are persistence of a moving particle system plus a thresholded field, not persistent fluid vortices. Shape continuity is strongest when bodies remain spatially close enough that their influence regions overlap; collisions, wall/obstacle interactions, gravity, and restitution alter that overlap over time. [ball.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/ball.js) · [box.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/box.js) · [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- The dominant Pi optimization lever is `res`: because work is roughly O(number of grid samples × particle amount), increasing `res` from 7 to 10 reduces sample count from about 9,393 to about 4,620 (roughly half), while reducing it from 7 to 4 increases samples to about 29,169 (roughly 3.1×). This follows the source formulas, not a Pi benchmark. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Practical Raspberry Pi 5 settings supported by this cost model: start at `res=10–14`, 30–50 particles, and `lerp` enabled; only move toward `res=7`/75 particles after measuring sustained FPS in the target browser. If contours are too blocky, lower `res` cautiously or keep `res` higher and accept fewer particles; if FPS collapses, increase `res` first because it reduces both field samples and cells. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- Keep `showParticles` off for a clean result and fewer extra p5 circle draw calls; do not expect it to reduce the expensive field loop, because the field still evaluates every ball regardless. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)
- A current practical browser implementation should treat this as CPU JavaScript + 2D canvas. A WebGL rewrite could move field evaluation/contouring toward shaders, but that would be an architectural replacement, not an option already present in this repository; p5 only enters WebGL when `createCanvas(..., WEBGL)` is requested. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js) · [p5 createCanvas](https://p5js.org/reference/p5/createCanvas/)
- Because the code uses `getMetaballDistance()` with no guard for `d²=0`, a sample exactly at a ball center yields division by zero (`Infinity` in JavaScript), which is harmless for threshold comparison but is another reason not to infer a numerically robust fluid solver from the visual result. [script.js](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js)

### Gaps
- No source-backed Raspberry Pi 5 FPS number, power/thermal result, browser benchmark, or tested browser flags is provided by this repository. Recommendations above are conservative settings derived from operation counts and the exposed controls; they should be validated on the actual Pi 5 deployment.
- No true fluid/advection implementation exists to compare against within this repository; claims of fluid behavior beyond rigid-body motion plus metaball rendering would be unsupported.
