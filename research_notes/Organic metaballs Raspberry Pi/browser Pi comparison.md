# Organic metaballs: browser and Raspberry Pi 5 comparison

## 1. What actually makes a persistent organic shape (rather than overlapping circles)?

### Takeaway
The defining operation is not drawing circles with alpha blending; it is evaluating a shared scalar field and extracting one iso-contour (or thresholded iso-surface) from that field. A neck appears when the contributions from two nearby primitives sum above the same threshold in the gap. Motion/attraction can make that neck persistent, but rendering alone cannot create a stable connection if the objects are kept too far apart.

### Cited Findings
- The p5.js reference implementation explicitly describes itself as an exploration of “isosurfaces,” using “the marching squares algorithm and linear interpolations” to approximate a curve. That is the essential distinction from two independently alpha-blended disks: [ZachLegros/metaballs README](https://raw.githubusercontent.com/ZachLegros/metaballs/master/README.md).
- The marching-squares reference explains the contour refinement step: interpolate the threshold between adjacent corner field values; with a threshold of 1, a 0.5-to-1.5 edge crosses halfway, while a 0.5-to-3 edge crosses nearer the lower-value corner. This interpolation is why a low-resolution field can still produce smooth-looking necks: [Marching Squares | Metaballs in JavaScript](https://jurasic.dev/marching_squares/).
- The three.js implementation is a genuine marching-cubes field extractor, described in source as “A marching cubes implementation,” and its source credits the classic WebGL blob sample. Marching cubes is the 3-D analogue of marching squares; both generate geometry from a field threshold rather than compositing circle outlines: [three.js `MarchingCubes.js`](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/objects/MarchingCubes.js).
- The current project’s SVG route has the same field-like visual mechanism without explicit grid sampling: all discs are first drawn into one shared buffer, then blurred and passed through a steep alpha threshold. Blur spreads alpha contributions; the threshold creates one connected iso-like silhouette. The existing implementation documents this in `sketch.js` (“blur + hard alpha step”), and its fixed spacing floor deliberately prevents fusion at weak attraction. This is a practical 2-D alternative to marching squares, not ordinary circle overlap.
- A persistent organic connection needs two coupled conditions: (1) the renderer’s field/threshold must permit a bridge, and (2) the update rule must let centers enter the bridge range and remain there. If physics enforces a separation greater than the field’s effective support, no renderer can create a neck; if the renderer only alpha-blends, proximity produces translucency/darkening, not a single contour.

### Inferences
- For this project’s 15 moving blobs, the existing “draw discs → blur → alpha threshold” pipeline is conceptually adequate for organic 2-D silhouettes and avoids marching-squares vertex generation. It should be described as a thresholded blur field, not as circles merely overlapping.
- A true sampled-field implementation gives more explicit control over contour topology and edge location. Use it if the design requires predictable thresholds, holes, narrow bridges, or a field independent of raster blur. For broad soft blobs on a fixed display, the shared-buffer SVG filter is likely cheaper to integrate.
- “Persistent” should be judged over time: attraction, repulsion, separation, and damping determine whether the field repeatedly forms and releases a neck. Rendering parameters alone only determine the shape at the current positions.

## 2. Where the browser cost goes: scalar sampling, contour extraction, fluid/advection, CPU versus GPU, and canvas/WebGL

### Takeaway
Dynamic metaballs have separable costs: moving particles, evaluating a scalar field, extracting/covering the contour, and compositing pixels. For a small 2-D population, CPU physics plus a low-resolution raster field can be practical; for high-resolution fields, many blobs, or fluid/advection, move field evaluation and/or advection to WebGL. GPU rendering does not automatically make CPU-side contour extraction cheap: the CPU/GPU boundary and readbacks can erase the gain.

### Cited Findings
- The GPU reference identifies its approach as a “GPU implementation of metaballs” for WebGL/WebGL2, using optimized marching cubes and three.js. Its input is generally a texture containing sphere positions (and optionally colours), while the output is a rendered image in a three.js scene: [sjpt/metaballsWebgl README](https://raw.githubusercontent.com/sjpt/metaballsWebgl/master/README.md).
- The same README gives a useful scale claim for the implementation—10,000 spheres at a 100×100×100 grid and 60 fps—while also warning that performance depends on the graphics card. Treat this as an implementation-specific demonstration, not a Raspberry Pi guarantee: [sjpt/metaballsWebgl README](https://github.com/sjpt/metaballsWebgl).
- Marching squares/cubes cost is governed primarily by field resolution and contour cells, while direct field evaluation is roughly proportional to cells × primitives if every cell tests every blob. Spatial culling, compact primitive textures, or a shader loop over a small fixed blob count reduce the practical constant. The references establish the field/contour method but do not publish a Raspberry Pi benchmark: [ZachLegros/metaballs README](https://raw.githubusercontent.com/ZachLegros/metaballs/master/README.md); [three.js MarchingCubes source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/objects/MarchingCubes.js).
- Fluid/advection is a different workload from static metaballs. A semi-Lagrangian fluid step typically requires one or more full-screen passes for velocity advection, force/divergence/pressure/projection, and dye advection. At 1024×600, every pass touches roughly 614,400 fragments; several passes per frame can dominate the cost even when only 15 metaball emitters are present. This is an engineering inference from full-screen sampling, not a benchmark from the reference implementations.
- WebGL’s fragment shader work is per-pixel. MDN’s WebGL guidance recommends moving work to the vertex shader where acceptable, reducing expensive fragment work, batching draw calls, and using appropriate precision; these principles apply directly to field evaluation and fluid passes: [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).
- Canvas 2-D and SVG-filter approaches can be attractive when the output is a single low-resolution layer and the browser’s compositor handles the blur. WebGL gives explicit control over render-target resolution, shader precision, ping-pong textures, and pass count, but adds shader compilation/context-loss/device-driver variability. The practical choice is therefore workload-dependent rather than “GPU always wins”: [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices); [MDN Canvas optimization](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas).
- CPU marching squares is easy to inspect and can produce a path/mesh, but it creates JavaScript loops, edge interpolation, and geometry uploads each frame. GPU field thresholding can keep the contour in a texture and avoid readback; reading pixels or generated geometry back to JavaScript synchronizes the pipeline and can be more expensive than leaving the result on-GPU.

### Inferences
- Recommended baseline for this repository: keep physics on the CPU; render 15 2-D metaballs at 0.5× or 0.4× display resolution; use one shared field/threshold pass; upscale once. This bounds fragment work while preserving smooth bridges.
- Use marching squares on the CPU only when the actual contour path is needed for interaction, collision, SVG export, or semantic geometry. Do not extract a CPU path merely to draw pixels.
- A WebGL fragment shader is the next step when SVG filters are unreliable or when fluid/advection is added. Store emitter positions/colours in a small uniform/texture input, evaluate the field per output pixel, threshold/smoothstep it, and keep the result on the GPU.
- For fluid motion, update a low-resolution simulation texture (for example 256×150 or 512×300), then composite/upscale to the display. Full native-resolution advection is the first thing to cut on Pi 5; it costs more predictably than reducing the number of emitters.
- Avoid claiming that “WebGL metaballs” means marching-cubes geometry is required. For a flat ambient 2-D display, a fragment shader field or thresholded raster is simpler and avoids 3-D mesh generation.

## 3. Raspberry Pi 5 recommendation and practical browser/WebGL decision

### Takeaway
Use Raspberry Pi 5 as a GPU-assisted kiosk, but design a measured fallback. Start with a low-resolution WebGL or existing raster pipeline, verify that Chromium is actually using hardware acceleration, cap the frame rate, and avoid readbacks. Retain a Canvas/SVG fallback for driver/context failures. For the current 15-blob ambient visual, do not introduce a fluid solver or CPU marching-squares mesh unless visual requirements justify its cost.

### Cited Findings
- Raspberry Pi’s product brief identifies the Pi 5 graphics subsystem as VideoCore VII and lists OpenGL ES 3.1 and Vulkan 1.2 support. That is hardware capability, not proof that a particular Chromium image, kiosk configuration, or WebGL path will sustain a target frame rate: [Raspberry Pi 5 product brief (PDF)](https://pip.raspberrypi.com/documents/RP-008348-DS-3-raspberry-pi-5-product-brief.pdf).
- Raspberry Pi’s official documentation has a graphics-driver/configuration section; use it as the platform source when checking the active Mesa/V3D stack rather than assuming the browser is accelerated: [Raspberry Pi configuration documentation](https://www.raspberrypi.com/documentation/computers/configuration.html#gl-drivers).
- Browser implementation details remain runtime-specific. Check Chromium’s `chrome://gpu` and the WebGL renderer at deployment time; “WebGL available” is not equivalent to “hardware accelerated.” MDN documents WebGL as a browser API with implementation-dependent limits and emphasizes testing on target devices: [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).
- The project currently pins p5.js 2.3.1 from jsDelivr and uses an SVG filter; its README recommends Chromium for the source sketch’s SVG canvas filter. This is a deployment dependency and a practical reason to test the exact browser rather than infer behavior from desktop Chrome: [project README](../README.md) (local project evidence).
- The current implementation already lowers filter cost with `MERGE_BUFFER_SCALE = 0.5`, performs one shared buffer pass, and uses a cheap upscale. Its own comment suggests trying 0.4 on a Pi. This is a sensible first Pi tuning knob because blur/filter work scales with pixel area (approximately quadratically with linear scale).

### Inferences
- **Preferred first deployment:** Chromium kiosk on Raspberry Pi OS Bookworm/modern Mesa, fixed 1024×600 logical output (or the panel’s native size), 0.5× metaball buffer, 30–60 fps cap, no pixel readback. Keep p5.js if the SVG path is stable on the target image; otherwise port the single shared-field operation to WebGL.
- **WebGL shader design:** use one full-screen quad and a small emitter array/texture; evaluate a smooth field and threshold in the fragment shader. Keep simulation/render resolution below native display resolution; composite colour separately if it reduces precision/overdraw. Prefer mediump where visual tests permit, but verify precision and banding on the Pi GPU.
- **Canvas/SVG fallback:** keep the current shared offscreen buffer rather than drawing 15 DOM/SVG nodes independently. If SVG filter performance is poor, replace only the filter stage with a 2-D canvas pixel/raster or WebGL field; preserve the CPU physics and attraction semantics.
- **Fluid/advection is optional, not the baseline:** a Pi 5 can plausibly handle a deliberately low-resolution fluid effect, but the additional full-screen passes, texture bandwidth, and context/driver risk are not warranted for persistent necks that a scalar field already provides.
- **Acceptance test:** record frame time over at least 30 seconds at the real panel resolution, while all 15 blobs move and repeatedly merge; test idle, worst-case overlap, and recovery/network input. Log whether WebGL is hardware accelerated, buffer scale, FPS, and throttling. Require stable frame pacing rather than a short benchmark peak.
- **Fallback ladder:** (1) reduce buffer scale 0.5→0.4; (2) cap at 30 fps; (3) reduce blur radius/filter passes; (4) lower WebGL fluid texture resolution or disable advection; (5) fall back to the shared Canvas/SVG renderer. Do not increase attraction or fake necks by inflating circles: that changes the topology/physics distinction the design depends on.

### Gaps
- No exact Pi 5 target panel refresh rate, OS image, Chromium version, or required FPS was supplied; recommendations are therefore configuration-agnostic and must be benchmarked on the kiosk image.
- The official Pi sources document hardware/driver capabilities, not an end-to-end browser metaball benchmark. Community reports may be useful for troubleshooting, but they should not replace deployment measurement.
- The three user-provided reference URLs are absent from this task context. If they are supplied later, map each one explicitly to: field representation, contour method, update/advection cost, browser API, and measured device behavior.
