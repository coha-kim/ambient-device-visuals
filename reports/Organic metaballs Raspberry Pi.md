# Make Raspberry Pi metaballs flow organically

The current sketch should **retain its CPU motion model and replace only the rendering backend in stages**, not jump to a fluid solver or return to independently rendered blobs. Its existing “one shared buffer → blur → alpha threshold” pipeline already has the essential metaball property: a connected silhouette comes from a shared field, while the reason blobs separate is that cross-population physics deliberately pushes their centres outside the field’s bridge range. The best first Pi 5 target is a low-resolution shared scalar field, rendered to a reusable Canvas 2D buffer and upscaled once; a single reduced-resolution WebGL fragment pass is the fallback when CPU profiling fails. Preserve `overallSize`, `speeds[]`, and `attractionStrengths[]` as the only live sensor contract, including the current population-indexed and asymmetric attraction semantics. Fluid/advection is warranted only if the desired visual is smoke-like history, trails, or vortices; it is not a cheaper way to obtain organic merged metaballs.

## The available references implement three different kinds of “metaball”

The requested three external references are not recoverable from this checkout or the supplied conversation: repository URL scanning found no three reference URLs, and the notes explicitly record that gap. It would be misleading to attribute the following findings to unnamed references. The comparison below therefore labels the three accessible implementations that the notes document: the **current ambient sketch**, **LeandroSQ/js-metaballs**, and **mx0c/metaball-fluid-simulation**. They expose three different choices: a raster goo filter, a direct field renderer, and a CPU sampled field with marching-squares polygons. A fourth, fluid reference is discussed later as an alternative rather than silently treating it as one of the missing three.

The current sketch draws all three populations—**15 orbs in total**—into one half-resolution p5 graphics buffer, applies `feGaussianBlur`, applies a steep `feColorMatrix` alpha transform, and upscales once ([project README](https://github.com/seoha-kim/ambient-device-visuals/blob/main/README.md); [current `sketch.js`](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js)). The filter’s important operation is not ordinary alpha overlap: blur spreads the combined alpha field and the color matrix thresholds it into a connected silhouette ([MDN `feGaussianBlur`](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/feGaussianBlur); [MDN `feColorMatrix`](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/feColorMatrix); [W3C Filter Effects](https://www.w3.org/TR/filter-effects-1/)). It therefore already has the right topology mechanism for a smooth neck, but its contour is defined indirectly by a browser SVG filter rather than by an explicit mathematical kernel.

LeandroSQ’s project is a direct per-pixel implicit field. For each pixel it sums a radius-weighted inverse-distance expression for every metaball, thresholds/remaps the sum, and colors the result; the GPU path evaluates this in a full-screen WebGL shader with a `MAX_METABALLS` limit of 20 ([README](https://github.com/LeandroSQ/js-metaballs/blob/master/README.md); [default fragment shader](https://github.com/LeandroSQ/js-metaballs/blob/master/src/assets/fragment_shader1.glsl); [GPU renderer](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/gpu-renderer.js)). Both its CPU and GPU implementations use squared distance, so the default source behaves like a radius-weighted inverse-square field rather than a conventional Euclidean `r/d` field ([CPU renderer](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/cpu-renderer.js); [math helper](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/extensions.js)). Its “organic deformation” is not mesh deformation: five circular primitives move and change radius, and their summed field crosses an isovalue to form or remove a neck ([blob source](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/blob.js); [main loop](https://github.com/LeandroSQ/js-metaballs/blob/master/src/scripts/main.js)).

The mx0c project samples a true 2D field, \(F(x,y)=\sum_i r_i^2/((x-x_i)^2+(y-y_i)^2)\), on a CPU grid and uses marching squares to fill the thresholded cells. Its README calls it a “toy 2D fluid simulation,” but the implementation contains rigid Matter.js bodies, not advection, pressure projection, viscosity, or a velocity field ([README](https://github.com/mx0c/metaball-fluid-simulation/blob/master/README.md); [field and contour source](https://raw.githubusercontent.com/mx0c/metaball-fluid-simulation/master/js/script.js); [Matter.js](https://github.com/liabru/matter-js/blob/master/README.md)). At its defaults, 75 particles on roughly a 93×101 sample grid imply about 704,000 field contributions per frame before contour drawing; the contour is immediate-mode p5 2D geometry, not a GPU mesh.

These implementations agree on the central fact: **a neck comes from summing influences before thresholding**, not from making two separately drawn circles look sticky. They differ in where the cost lands. SVG blur delegates raster/filter work to the browser compositor; direct WebGL keeps field evaluation in one fragment pass; marching squares adds an explicit contour scan and polygon rasterization. None of the cited projects supplies a Raspberry Pi 5 benchmark at this project’s 1024×600 output, so their performance claims are structural, not deployment guarantees.

## The current sketch separates because physics defeats its own goo field

The diagnosis is in the update order and the meaning of `mergeAmount`. `Orb.applyCrossPopulationForces()` resets `mergeAmount` every frame and derives it from the current pair distance; there is no bond graph, cluster state, hysteresis, or retained field history ([current force code](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js#L389-L430)). `renderOrbLayers()` then enlarges a disc by only `0.18 * mergeAmount`, draws it into the shared raster, and relies on blur/threshold for the visible bridge ([current renderer](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js#L227-L303)). That is a visual overlap aid, not persistence.

More importantly, `resolveCrossPopulationSeparation()` runs after motion and enforces a population-pair spacing floor. At low attraction it uses approximately `overallSize * BOUNCE_SEPARATION`; the source comments describe this as the guarantee that weakly attracted populations bounce apart ([separation code](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js#L304-L338)). The renderer cannot make a durable neck if this solver repeatedly moves centres beyond the filter’s effective reach. The apparent regression to “separate blobs” is therefore **not primarily a bad blur setting**. It is the intended consequence of recomputing a proximity scalar and then enforcing separation.

The correct conceptual split is: the field determines the instantaneous contour; physics determines whether centres enter and remain in the contour’s bridge range. If the product requirement is only more organic silhouettes, keep the current physics and improve the field. If it is “once joined, remain joined for a while,” add a small merge state machine or cluster rule. A field-only replacement cannot create semantic persistence after the centres have been forced apart. Conversely, adding sticky dynamics without a shared field produces attached circles, not a coherent organic shape.

## Replace the filter backend, not the motion contract

The recommended architecture is a staged **CPU physics + shared scalar-field renderer**, with a WebGL field backend behind the same renderer interface. Keep `Orb.update()`, `Orb.wander()`, `Orb.applyCrossPopulationForces()`, the current population colors, and the public `updateParamsFromSensor(data)` entry point unchanged at first. Replace `renderOrbLayers()` with a field renderer that evaluates all active orbs into one logical grid, thresholds only after summing all contributions, computes population color by contribution weights, and upscales the completed image once. This is the smallest change that directly addresses organic necks without changing the portable-device-visuals integration.

Start with a **256×150 logical field** for the 1024×600 output, retaining a reusable `ImageData`/typed buffer and updating it at 15–30 Hz while the display presents the last completed field between updates. That is about 38,400 samples; 15 naïve contributions are roughly 576,000 evaluations per field update. The current 512×300 merge buffer is about 2.30 million pixel/ball evaluations if implemented as a direct CPU field, and native 1024×600 would be about 9.22 million. Test 160×94, 256×150, 320×188, and 512×300 rather than treating one resolution as universal. Use a compact-support kernel or per-ball influence bounds so distant cells do not evaluate every orb; use uniform bins only if profiling shows the scene is sparse enough for the bookkeeping to pay back.

Use a kernel whose visible reach is calibrated against the existing SVG screenshots. A practical normalized form is

\[
F(x,y)=\sum_i w_i\,K\left(\frac{d_i}{R_i}\right),\qquad
K(q)=\begin{cases}(1-q^2)^2,&q<1\\0,&q\ge1,\end{cases}
\]

where \(R_i\) is the field radius and the contour is `smoothstep(iso - edge, iso + edge, F)`. This compact polynomial is bounded, avoids the inverse-square singularity at a centre, and makes culling possible. An inverse-square kernel is closer to the mx0c and LeandroSQ references, while the polynomial is easier to budget and tune. Do not mix separate per-population thresholds: calculate one total field first, then blend color according to each population’s contribution, or bridges will split into layered silhouettes.

If CPU field writes miss the frame budget, use the same equation in one reduced-resolution WebGL fragment pass. Upload a small `Float32Array` of positions, radii, and population weights once per update; draw one full-screen triangle; keep all color mapping and upscaling on-GPU; never call `readPixels()` in steady state because it forces a synchronization and CPU round trip ([MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)). Pi 5’s VideoCore VII supports OpenGL ES 3.1, but that only makes WebGL a viable candidate; browser, Mesa, compositor, context type, and shader precision still require measurement ([Raspberry Pi 5 specifications](https://www.raspberrypi.com/products/raspberry-pi-5/)).

## Preserve portable parameters with explicit, one-way mappings

The live contract is already narrow: `overallSize`, indexed `speeds[]`, and indexed `attractionStrengths[]`; missing entries are left unchanged by `updateParamsFromSensor()` ([current parameter adapter](https://github.com/seoha-kim/ambient-device-visuals/blob/main/sketch.js#L180-L202)). Preserve that contract and do not expose grid resolution, field threshold, kernel cutoff, persistence time, noise amplitude, or renderer mode to portable-device-visuals. Those are deployment/rendering controls, not device semantics.

| Portable input | Preserve current meaning | Renderer/physics mapping |
|---|---|---|
| `overallSize` | Pixel-scale blob size, currently 65 after v7 | Keep the current clamp and use `R_i = OUTER_RATIO * overallSize * FIELD_REACH`; do not alter attraction or grid resolution from this value |
| `speeds[p]` | Population `p` wander rate and movement magnitude | Leave `noiseAccumByPop[p] += NOISE_BASE * speedByPop[p]` and `MOVE_BASE_PX * speedByPop[p]` unchanged; never use speed to inflate field radius |
| `attractionStrengths[p]` | Attraction of population `p` toward other populations, asymmetric by owner | Keep `mergeTFor(p)` and current force semantics; use a documented pair policy such as `max(mergeT(a), mergeT(b))` for bridge/bond eligibility, while retaining each owner’s force independently |
| colors | Fixed ambient palette, portable owns population 1 | Preserve field-contribution color mixing and the existing palette; do not introduce sensor color mutation |

For the current portable mapping, population 1’s attraction falls from the baseline `1.3` as intensity rises and recovers over the configured 30–120 second range; the field must not reinterpret that signal as size, speed, or color. The current v7 `overallSize=65` and the portable’s clamped size range should continue to produce the same physical-radius relationship. At a later stage, if “joined after contact” is explicitly required, derive a pair bond from attraction without changing the sensor schema: on contact above a threshold, hold a bond for a short time; release only after distance exceeds a larger hysteresis threshold for a release duration. For bonded pairs, bypass the ordinary cross-population separation floor but retain a cluster anti-collapse radius.

Migration should proceed without deleting the current SVG path. First add a renderer switch and diagnostics, defaulting to SVG. Second implement the scalar field at the existing 0.5 logical scale and compare screenshots with identical orb positions. Third add compact support, typed-array reuse, reduced update cadence, and 256×150 benchmarking. Fourth add the WebGL backend only if CPU timing fails. Fifth, if semantic persistence is required, add bond state and tests for contact, one-frame separation, sustained release, re-contact, and a third population joining an existing cluster. Keep the SVG backend as a runtime fallback for context loss or field-renderer failure.

## Budget work around 38,000 cells, not 614,400 display pixels

The low-GPU baseline is a low-resolution Canvas field: one reusable `ImageData`, one `putImageData`, one upscale, no SVG filter region expansion, no per-orb DOM, and no marching-squares geometry. Store positions/radii/colors in typed arrays; avoid per-cell objects, closures, temporary arrays, strings, and repeated canvas creation. Advance motion from elapsed `requestAnimationFrame` timestamps rather than frame count ([MDN `requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)). A 15–30 Hz field update is appropriate for an ambient display if motion interpolation is acceptable; it trades temporal smoothness before it sacrifices contour quality.

Use compact influence bounds and a uniform spatial bin if average candidate count drops materially. Dirty rectangles help only when motion covers a small portion of the scene; 15 continuously wandering orbs will often cover most of the 256×150 grid, so measure before adding complexity. If the main thread becomes contended, `OffscreenCanvas` can move rendering to a worker, but it changes scheduling and responsiveness rather than reducing arithmetic ([MDN `OffscreenCanvas`](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)).

The WebGL alternative should remain one pass at one reduced internal resolution. Use a fixed active-ball loop or a small texture-backed ball list, appropriate `mediump` precision after visual validation, one fullscreen primitive, and no postprocess bloom, blur, or readback. A 1024×600 fullscreen path would touch about 36.9 million fragment locations per second at 60 display frames before shader instruction cost; reducing the field to 256×150 cuts that coverage by 16×. WebGL is likely to reduce CPU work, but **it is not evidence of lower GPU energy than SVG**. The current project’s SVG claim is unverified, and no cited source measures these exact backends on Pi 5.

Treat thermal and power conditions as part of the budget. Raspberry Pi recommends a high-quality 5 V/5 A supply and active cooling for Pi 5’s best performance ([Raspberry Pi 5 specifications](https://www.raspberrypi.com/products/raspberry-pi-5/)). The validation run must use the real Chromium kiosk, OS image, display, compositor, cooling, and network setup. Record renderer/context and GPU string, logical/output resolution, update rate, median and p95 frame time, dropped frames, CPU/GPU utilization, temperature, and watts. Run cold-start and at least a 10-minute steady-state test. Compare SVG, CPU field, and WebGL field at equal visual quality; do not choose from FPS alone.

## Alternatives clarify when replacement is justified

Marching squares is warranted when the application needs an explicit contour: collision geometry, hit testing, SVG export, a crisp path, or a topology-aware semantic boundary. It samples four corners per cell, selects one of 16 cases, and interpolates threshold crossings ([Wikipedia, Marching squares](https://en.wikipedia.org/wiki/Marching_squares); [Jamie Wong](https://jamie-wong.com/2014/08/19/metaballs-and-marching-squares/)). At 256×150 it scans about 37,995 cells, but it still adds interpolation, segment storage, ambiguous saddle handling, and Canvas path/polygon rasterization. For this ambient filled image, direct raster thresholding is cheaper and simpler; use marching squares as a correctness prototype or only when a path is a requirement.

Fluid simulation is warranted when the design asks for **history-dependent flow**: trails that persist after a source moves, vortices, dye transport, viscosity, or smoke-like deformation. A representative WebGL fluid implementation allocates velocity, dye, divergence, curl, and ping-pong pressure buffers, then performs advection, vorticity, divergence, several pressure iterations, projection, and dye advection ([PavelDoGreat fluid source](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/master/script.js)). That is multiple full-grid passes per step, not a cheaper metaball renderer. If chosen, keep a separate 128–256-wide simulation grid, reduce pressure iterations, disable bloom/sunrays first, and composite the result as an optional accent behind or inside the metaball layer. Do not replace the stable sensor-driven blob model with a fluid solver merely to fix neck persistence.

The direct WebGL metaball route is the strongest replacement if CPU field timing fails and the target browser has a reliable context. The low-resolution CPU field is the strongest default if low WebGL/GPU consumption and deployment simplicity dominate. The current SVG path remains the visual reference and fallback because it already produces broad organic silhouettes with minimal code churn. The mx0c rigid-body/marching-squares approach is useful for understanding explicit contours, but its Matter.js physics and immediate-mode polygons are not a good dependency or rendering model for this fixed 15-orb ambient display.

## Conclusion

The project does not need a new blob simulation to look organic: it needs one shared field whose threshold is tuned independently from centre motion, plus an explicit decision about whether “merged” means visual contact or persistent bonding. Replace the SVG renderer incrementally with a compact scalar field, start at 256×150 and 15–30 Hz, preserve the three existing sensor inputs exactly, and add hysteretic bonds only if product acceptance tests demand persistence after separation. Use WebGL as a measured CPU-relief option, not as an assumed low-power answer.

The decisive validation is an apples-to-apples Pi 5 run under the real kiosk stack. If SVG meets the frame and thermal budget, keep it. If CPU field rendering is predictable and uses less GPU, keep the Canvas backend. If CPU misses while WebGL remains stable, use the single reduced-resolution fragment pass. Adopt marching squares for explicit contours and fluid simulation for actual flow semantics—never as default substitutes for the shared metaball field.
